## 结论与验证范围

发现 5 项可以在隔离环境复现的问题：2 项 P1，3 项 P2。本次仅新增审查报告和模拟诊断脚本，没有修改业务逻辑。

审查链路：Electron 启动与 IPC 握手 → React 配置加载和编辑 → HTTP 参数校验与 SSE 同步 → AutomationBridge 状态转换 → Resolver 免费/付费资格、链接与冲突保护 → Runner 填单、递补、整页提交 → 取消、排空与释放运行锁。

验证结果：现有 205 项测试全部通过，无跳过；`npm run typecheck` 通过。额外诊断使用真实 Node HTTP 服务、当前发布的前端资源、无头 Edge 的真实 DOM，以及模拟的 EventSource 和平台操作。所有数据写入临时 `R3_DATA_DIR`；没有调用真实搭剧提交接口。平台失败与弹窗关闭的组合是受控故障注入，不表示已经观察到线上平台出现该组合。

## 1. P1：未知填单异常仍递补同一槽位，后续成功会抹掉不确定状态

位置：`src/platform/stage.ts:2127`、`src/runner.ts:774`、`src/runner.ts:606`、`src/platform/stage.ts:2166`。

非内容/商品选择错误被包装为 `STAGE_DRAMA_FILL_FAILED`，主循环却仅对 `STAGE_TASK_BLOCKING_FAILURE` 立即停止。其他错误均进入同槽位递补，且 cleanup 自身会吞掉异常。下一部填写成功将页面级 `fillUncertain` 重置为 false，最终收尾保护因此不能阻止这条路径。

复现：容量为 1，输入 A、B；A 填单抛出“保存结果不确定”，B 返回成功。观测到填单调用依次为 A/槽位1、B/槽位1，随后提交整页；Bridge 最终 `completed`，`lastError=null`。

影响：不能保证 A 尚未保存或已安全放弃修改；程序会继续编辑结果不确定的槽位。A 被标记为普通失败后还能进入失败重跑。这与“进入填单并阻塞后保留原有停止保护”的要求不一致。

建议：只允许明确、已确认放弃修改的内容/商品选择耗尽继续递补。普通填单异常、保存结果不确定、取消或 cleanup 失败均停止；不确定状态不能由另一部填写成功清除。补充“A 失败后 B 可用”和“cleanup 失败后还有下一部”的回归覆盖。已有单部填单失败测试仅覆盖队列结束时收尾报错，未覆盖此路径。

## 2. P1：SSE 初始化或重连覆盖用户付费模板，并影响下一次启动参数

位置：`src/web/client/src/hooks/useSSE.ts:53`、`:62`，`src/web/client/src/App.tsx:78`、`:189`，`src/web/automation_bridge.ts:71`。

可编辑配置与运行快照共用同一个 `state.paidTemplate`。`/api/config` 载入文件配置后，SSE 的 `init` 或 `state_change` 无条件合并 Bridge 的默认或上次运行模板。Bridge 空闲默认值为“超超小额”，不代表当前已保存的配置。

复现：模拟配置接口返回“中额”，前端成功选中中额；随后发送空闲 `init`，模板切换到“超超小额”。点击“开始执行”，捕获 `/api/start` 请求的 `paidTemplate` 为“超超小额”。这验证了配置变化确实传递到启动请求。

影响：刷新、SSE 重连或配置加载的时序变化可能使下一次运行使用错误付费面板；运行期间修改模板也可能被后续运行状态覆盖。

建议：独立管理“待执行配置”和“当前运行快照”，SSE 只更新运行状态；重连不能改写用户配置。覆盖配置先返回/SSE 后返回、运行中修改配置、重连后启动三种顺序。

## 3. P2：弹窗关闭被直接判定为保存成功，忽略已经出现的失败信息

位置：`src/platform/stage.ts:1552`、`:1610`，`src/platform/stage_network.ts:67`。

`waitStageSubmitResult` 虽监听 XHR 和错误提示，但最终只要 `hiddenPromise` 成功，就直接返回成功；既不检查响应业务码，也不优先处理已经发现的保存错误。XHR 监听范围还包含同 API 前缀下的任意修改请求，因此不能证明观察到的是当前保存操作。

复现：真实 DOM 显示“保存失败”提示，注入一个 HTTP 400 保存响应，然后关闭编辑弹窗；`waitStageSubmitResult` 正常 resolve，没有抛错。

影响：在失败后弹窗关闭、用户手动关闭或平台自动关闭等情形下，程序可能把未确认保存的剧目记为已填写，并继续整页提交。

建议：观察由本次点击触发的准确保存请求，核验 HTTP/业务成功结果，并验证槽位保存后的实际值。无法确认结果时停止；已明确检测到的错误不能被弹窗关闭覆盖。增加 HTTP 400、HTTP 200 业务失败、非保存 XHR、失败提示后关闭弹窗的覆盖。

## 4. P2：批量输入使环境检查 URL 超限，且前端静默保留旧状态

位置：`src/web/client/src/hooks/useEnvironment.ts:16`、`:17`、`:23`，`src/web/server.ts:191`。

每次输入变化和定时轮询，都将完整剧目列表 URI 编码后放到 GET 查询参数。后端开始处理之前，Node HTTP 解析器就可能拒绝过长请求。接口允许最多 10000 条输入，与这条环境检查链路的长度能力不一致。

复现：200 条正常长度的中文测试剧名，URL 为 38924 字节，服务返回 HTTP 431。前端 `res.json()` 失败后进入空 catch，不清除旧 `envInfo`，也不提示检查失败。

影响：合法批量列表无法刷新环境检测，界面可能继续展示上一份检测状态。是否超限由编码后的总长度决定，不是固定的剧目数量。

建议：通过请求体传输列表，或仅传后端检测实际需要的输入模式；检查非 2xx 响应，显示检测错误或过期状态。增加长列表和请求失败覆盖，同时避免旧请求晚返回覆盖新输入的检测结果。

## 5. P2：配置保存失败后已经部分写入，前端与磁盘状态不一致

位置：`src/web/server.ts:252`、`:270`、`:273`。

配置请求经过整体验证后，按顺序直接覆盖多个文件；后面的写入失败不会恢复已经保存的字段。

复现：临时 ROI 原值 0.95，将付费面板文件路径设置为目录以注入文件系统写入故障，提交 ROI=1.25、模板=中额。接口返回 HTTP 500，但 ROI 文件已经变成 1.25。

影响：用户看到“保存失败”，重载或下次运行却可能采用部分新配置。锁定文件、磁盘故障等写入失败也存在相同路径。

建议：用单一配置文件原子替换，或在多文件写入中实现可恢复事务；失败时返回明确的已保存字段并同步前端也比当前静默部分保存更可控。补充第二个文件写入失败的故障注入测试。

## 已核对的保护与限制

- 桌面启动通过实例标识和子进程 PID 校验 IPC，就绪地址来自本次启动的后端；退出等待 Bridge 收尾。
- HTTP 服务绑定 loopback，修改请求检查同源 Origin；配置和启动使用严格 Zod 校验。
- 长平台 ID 保持字符串，内容接口响应使用无损 JSON 解码。
- 当前作品资格重新查询，并检查两渠道返回的抖音作品 ID 一致。
- 获取运行锁后刷新冲突记录；不确定任务提交阻断继续运行。
- 整页提交使用本次请求关联，结果不确定不自动重复提交；冲突递补限定为当前运行填写的槽位。
- 取消流程保持运行中状态直到排空；Runner 在 `drain()` 后释放锁。未发现恢复旧 checkpoint 的路径。
- 无候选空页可以完成而不提交复制模板；零处理量成功率已经为 0%。

上述结论是源码与现有模拟测试支持的范围，不等于生产平台全部版本、真实网络故障或真实 Windows 文件故障均已实测。
